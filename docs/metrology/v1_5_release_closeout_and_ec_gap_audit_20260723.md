# V1.5 发布收口、代码清理与 EC 物理能力差距审计

日期：2026-07-23

## 1. 结论

当前 V1.5 已形成较完整的离线自动化、证据治理、成熟旧算法执行合同和 Web 平台骨架，但还不能定义为“已经完美”或“已经完成真实发布验收”。

当前最准确的状态是：

- 成熟 V1.5 原生执行链可识别、可审计、可做离线门禁。
- 正式 CO2/H2O 队列已增加源码级隔离检查，禁止导入 V2 或移植执行模块。
- 压力、露点、温度、滤波比值、物理判稳、失败点隔离和拟合输入溯源已有明确合同。
- 新旧算法都可以保留，但生产身份、参数命名、工件角色和放行结论必须隔离。
- 当前工作树包含大量未分组改动和新文件，不适合直接推送为一个发布提交。
- 当前机器缺少压力控制器、数字压力计和露点仪，无法完成真实静态全链验收。
- 现有 45 点 CO2 和 13 点 H2O 静态校准不能替代 EC 动态性能验收。

因此下一阶段应是“发布收口”，而不是继续往旧入口里叠加功能。

## 2. 正式路径身份

### 2.1 唯一允许的成熟生产路径

正式 V1.5 必须使用：

- 路径身份：`native_mature_v1_5_0613_0620_0621`
- 算法身份：成熟 V1.5 `legacy_ratio`
- `migrated_algorithm = false`
- 正式采样：1 Hz
- `AVERAGE1/AVERAGE2 = 49`
- 拟合输入：滤波后比值
- 压力：实际压力
- H2O 参考值：实际露点和实际压力推导

“0613/0620/0621”在这里表示经锁定的原生成熟 V1.5 合同，不表示后来仿照或移植出的同名执行路径。

### 2.2 禁止误用的路径

正式队列不得直接或间接切换到：

- V2 runner、adapter 或 profile
- 迁移版算法入口
- 新吸光度算法生产入口
- V1 早期旧拟合入口
- 为诊断、回放、影子评估或兼容而保留的工具入口

当前新增的源码隔离门禁会检查以下四个核心运行文件的 Python 导入：

- `run_v1_5_formal_co2_open_flow_queue.py`
- `run_v1_5_formal_h2o_open_flow_queue.py`
- `run_v1_5_formal_open_flow_sampling.py`
- `run_v1_5_formal_h2o_open_flow_sampling.py`

只要导入 `gas_calibrator.v2...` 或 `v2...`，成熟路径合同即判定为 blocker。

### 2.3 仍需解耦的结构性混淆

少量 V1.5 数据库初始化代码复用了 `gas_calibrator.v2.storage`。这不是正式拟合或气水路执行依赖，但命名上容易造成误判，也增加未来维护风险。

发布前应把这部分公共数据库能力迁移到中性命名空间，例如：

- `gas_calibrator.storage`
- `gas_calibrator.persistence`
- `gas_calibrator.evidence_store`

V1.5 和 V2 都只依赖公共层，不允许 V1.5 反向依赖 V2 命名空间。

## 3. 当前代码结构问题

### 3.1 主要问题不是字节级重复

现有源码扫描未发现成组的完全相同文件。真正的问题是：

- 入口数量过多，正式、诊断、回放、迁移、影子和历史工具混在相近目录。
- 大文件承担了过多职责，修改边界不清楚。
- `tools` 中既有薄命令行入口，也有大量业务逻辑。
- 活跃生产代码和历史参考代码都可被普通导入或直接运行。
- 大量工作树和分支缺少统一归档状态，容易从错误基线继续开发。
- 临时浏览器、缓存和运行工件曾进入工作树视野，增加审查噪声。

### 3.2 高风险大模块

优先治理对象：

- `workflow/runner.py`
- `ui/app.py`
- `v1_5/web_console/server.py`
- V1.5 full-flow 编排模块
- 正式 H2O 采样模块
- V2 的多个大型 facade

第一轮不应改行为，只做“外观不变的职责拆分”：

1. 保留原公共入口作为 facade。
2. 按设备、物理门禁、采样、拟合、证据、数据库、报告拆出内部模块。
3. 每次只迁移一个职责，并由现有回归测试锁住输入输出。
4. 未完成 parity 前，不删除原函数或改变默认入口。

## 4. 建议的代码分层

### A. 生产原生层

仅包含正式 V1.5 原生成熟运行所需代码：

- 成熟 CO2 45 点和 H2O 13 点队列
- 正式采样
- 原生物理门禁
- 成熟旧算法拟合
- 受控系数读写
- 正式证据与放行评审

要求：

- 禁止依赖 V2 或迁移执行模块。
- 禁止从诊断脚本反向调用生产链。
- 每个正式入口都有唯一 route/profile identity。
- 所有运行工件记录源码版本、配置哈希、气瓶证书、设备映射和方法版本。

### B. 公共基础设施层

包含 V1.5/V2 都可复用、但不拥有校准算法语义的能力：

- 数据库存储
- 工件注册
- 哈希和 lineage
- 通用串口协议解析
- 通用时间与单位处理
- 报告和证书基础组件

要求：

- 使用中性命名空间。
- 不包含 V1.5/V2 的默认算法选择。
- 不允许公共层反向启动真实气路或设备写入。

### C. 诊断和影子层

包含：

- replay
- historical audit
- shadow absorption
- parity
- dry-run
- simulation
- engineering probe

要求：

- 文件名、CLI 帮助和工件中明确标记用途。
- 默认 no-write。
- 不能生成正式放行结论。
- V2 真机探针继续遵守 Step 3A 双重解锁和 promotion blocked 规则。

### D. 历史参考层

包含早期 V1、迁移尝试、一次性修复脚本和已替代方案。

处理方式：

1. 先生成引用清单和最后使用日期。
2. 移入 `archive/legacy_reference` 或独立历史 tag。
3. 从正式入口发现列表中排除。
4. 保留两个发布周期。
5. 确认无导入、无文档引用、无工件依赖后再删除。

不建议直接大批删除，因为历史脚本仍可能解释旧校准证据。

## 5. 物理与计量能力审计

### 5.1 当前已经具备的正确方向

- 压力优先的 SENCO9 流程。
- CO2 零气与 H2O 干气点分离。
- CO2 证书值与实际压力参与参考计算。
- H2O 使用实际露点和实际压力推导参考水含量。
- 区分水面/冰面饱和蒸气压模型并记录模型版本。
- 使用滤波后 CO2/H2O ratio 进入成熟拟合。
- 记录温箱温度、分析仪腔温、露点斜率和压力状态。
- 识别 ratio 冻结、串口覆盖不足和尾窗不稳定。
- 点失败后不进入拟合，正式整轮不得用挑点方式伪装完整。
- S1/S3、S2/S4 主拟合与 S5/S6 最终仿射修整在语义上分开。
- 正式 1 Hz 与结束恢复 10 Hz 的用途分离。
- 原始证据、处理结果、拟合输入和最终结论有 lineage 方向。

### 5.2 尚未闭环的静态物理问题

- 串联多台分析仪只记录了位置，还没有完整的流量、管容、停留时间和压降模型。
- 未建立每台设备随串联位置变化的气体到达时间修正。
- H2O 吸附/解吸滞后、壁面浸润和干湿历史仍需显式状态模型。
- 吹扫判稳主要依赖观测阈值，尚未形成“气源切换响应 + 露点 + ratio + 时间常数”的联合物理判稳。
- 真实压力控制器、数字压力计、露点仪的当前机闭环证据缺失。
- 当前气瓶证书、标准器证书、重复性和分辨力尚未形成完整的当前批次不确定度预算。
- VENT 在生产与测试配置中的语义差异需要统一。

### 5.3 EC 动态性能缺口

EC 系统的关键要求不只是静态浓度准确度。仍需独立建立动态验收：

- 10 Hz 原始采样连续性和时间戳抖动
- CO2/H2O 阶跃响应的 t10、t50、t90
- 各分析仪和串联位置的传输延迟
- CO2、H2O、温压与风速数据的时间同步
- 管路衰减和频率响应
- 交叉谱、协谱和相位响应
- 高频噪声、零点漂移和 Allan deviation
- 干湿切换的吸附/解吸滞后
- 不同流量、压力和管长下的动态修正
- 动态补偿前后对通量的影响

通过静态 45 点/13 点只能证明静态校准能力，不能证明 EC 动态通量性能。

## 6. 真机验收顺序

当前压力控制器、数字压力计和露点仪未连接，因此只能准备或执行不依赖这些设备的受控检查。

### H0：设备库存与只读遥测

前提：用户对具体真机检查明确授权。

- 查询四台分析仪和继电器/温箱/湿度发生器的设备身份与状态。
- 不改变采样频率。
- 不切换气水路。
- 不写 ID、SN 或系数。
- 不作为 real acceptance。

### H1：公共标准器恢复后的集成检查

- 校验压力控制器、数字压力计和露点仪时钟与单位。
- 比较压力控制器和数字压力计的偏差与稳定度。
- 检查露点仪响应、斜率、回弹和异常冻结。
- 验证 vent、阀组和实际气源映射。
- 完成 Q1-Q4/E0-E4 当前机证据。

### H2：静态真实验收

- CO2 45/45 干净有效。
- H2O 13/13 干净有效。
- 不混失败点、旧批次和零散复验点。
- 先 no-write 多策略评审，再受控写入。
- 写后按最小必要点复验。
- 形成完整不确定度与证书工件。

### H3：EC 动态验收

- 10 Hz 阶跃、延迟、频响、噪声和同步测试。
- 建立串联位置的传输模型。
- 评估动态修正对协方差和通量结果的影响。
- 静态合格和动态合格分别出结论。

## 7. Git 和云端发布策略

### 7.1 当前不应直接推送

当前成熟工作树存在大量已修改和未跟踪文件，且当前分支与 `origin/main` 有较大双向分叉。把所有内容作为一个提交推送，会导致：

- 无法区分生产门禁、Web、数据库、文档和实验代码。
- 无法进行可靠回滚。
- 难以确认哪些文件来自用户已有改动。
- PR 审查无法聚焦。

### 7.2 推荐的发布分组

在新的干净 release worktree 中按主题迁移并逐组验证：

1. 原生成熟路径身份和物理门禁。
2. 拟合输入、失败点隔离和写前评审合同。
3. 公共存储层解耦及数据库迁移。
4. 计量资产、证书、不确定度和 lineage。
5. Web 工作台和中文产品体验。
6. 测试、文档和发布工件治理。

每组独立提交，最后通过 PR 推送，不直接合入 `main`。

### 7.3 工作树与分支治理

当前本机存在大量工作树和分支。清理前必须先输出：

- 工作树路径
- 分支
- HEAD
- dirty/clean
- upstream
- 是否已合并
- 最后提交时间
- 建议保留、归档或删除

只允许自动删除“干净、已合并、无独立提交、非当前运行依赖”的工作树。其余必须保留或经用户确认。

## 8. 发布完成标准

只有同时满足以下条件，才能称为 V1.5 发布收口完成：

- 正式入口全部归类，未分类数量为 0。
- 原生成熟运行源码的 V2/移植依赖数量为 0。
- V1.5 不再依赖 `gas_calibrator.v2.storage`。
- 正式配置、队列和气瓶证书哈希固定。
- focused、formal gate、parity、resilience 和中文 UI 测试通过。
- 干净 release worktree 可重复构建。
- 变更按主题提交，可审查和回滚。
- 云端 PR 已建立，CI 通过。
- 当前机真实静态验收与 EC 动态验收状态分别标明。

## 9. 下一步执行顺序

1. 完成本次门禁和审计变更的 formal gate 回归。
2. 生成全量工作树/分支治理清单，不立即删除。
3. 建立公共存储层解耦任务，消除 V1.5 对 V2 命名空间的反向依赖。
4. 建立干净 release worktree，按六组主题迁移。
5. 对大模块做 facade-preserving 拆分，不改变行为。
6. 在公共标准器恢复后执行 H1/H2。
7. 单独建设并验证 EC 动态验收 H3。

这条路线可以让代码结构变清楚，同时保持成熟 V1.5 生产能力和历史证据不被破坏。
